## 2. 工程结构：为什么这么切

- **`cofinance_core`（静态库）+ `cofinance`（可执行）+ `cofinance_tests`（测试）三个 target。**
  测试必须能链接到业务代码，而 `main()` 是不可链接的（同一个进程里不能有两个 main）。把除 `main.cpp` 外的所有实现放进静态库，测试直接链它，这是 C++ 项目最常见的可测试性切分。
- **不用 `file(GLOB ...)` 收集源码。** GLOB 在「新增文件」时不会触发 CMake 重新配置，表现为「我明明加了文件却不参与编译」这种诡异现象。宁可手写文件列表。唯一例外是测试目录用了 GLOB —— 因为那里新增用例文件的频率很高，且失败现象无害（重新 configure 即可）。
- **依赖全部 `REQUIRED`，配置阶段就失败。** 缺库时 CMake 直接报「找不到 XXX」，而不是让你编译到一半看到满屏 `undefined reference`。把错误暴露在最便宜的阶段，是工程上的通用原则。
- **告警选项按 target 设置（`target_compile_options`）而不是改全局 `CMAKE_CXX_FLAGS`。** 后者会污染第三方代码（vendored 的 nlohmann/json 之类）并让你无法只对部分代码放宽标准。

## 3. 异步日志（本阶段核心）

### 3.1 为什么不能在业务线程里直接写盘

一次 `write()` 落盘涉及的代价：用户态/内核态切换、可能的磁盘 IO、文件锁与 inode 竞争。在并发服务里，代价不止是「慢」，而是**放大**：多个业务线程争抢同一把文件锁 → 相互阻塞 → 一个慢磁盘拖垮整个线程池。日志是**可观测性设施**，绝不能反过来成为服务的瓶颈或故障源。

所以设计目标是：**业务线程只做「格式化 + 入队」，落盘交给唯一的后台线程**。业务线程的日志开销被压缩到「一次内存分配 + 一次加锁入队」。

### 3.2 三种方案对比

| 方案 | 业务线程开销 | 丢日志风险 | 实现复杂度 | 我们的选择 |
|---|---|---|---|---|
| 同步直写文件 | 高（系统调用 + 磁盘 IO 在关键路径上） | 无 | 极低 | ✗ |
| **有界队列 + 单后台线程** | 低（格式化 + 入队） | 队列满时可控丢弃 | 中 | ✅ P0 采用 |
| 无锁双缓冲（前端缓冲/后端缓冲互换） | 更低（几乎无锁竞争） | 同上，且更难观测 | 高 | ⏳ P11 优化目标 |

选有界阻塞队列的理由：它**正确性容易论证**（锁 + 条件变量，行为可推理），而且能把「背压策略」讲清楚。双缓冲是性能优化，等 P11 有压测数据后再做——**先正确，后快**，并且用数据证明快了，而不是凭感觉。

### 3.3 为什么队列必须有界

无界队列看起来「永不丢日志」，但它把「日志打得太多」从**性能问题**升级成了**内存问题**：一旦下游写盘速度跟不上，队列会无限增长直至 OOM 把进程干掉。有界队列把故障模式变得可控可观测——丢弃 + 计数，而不是崩溃。

### 3.4 背压策略是分级的（`Logger::enqueue`）

- `DEBUG` / `WARN`：队列满 → **直接丢弃并计数**。理由是它们属于诊断信息，丢掉的损失小于阻塞业务线程的损失。
- `ERROR` / `FATAL`：队列满 → **最多等 100ms** 等后台线程腾空间，仍满则**退回同步写 stderr**。理由是「致命信息宁可拖慢，也不能丢」。
- 这个「分级」是刻意设计的：如果所有级别一视同仁，要么业务被日志拖死，要么关键错误被丢掉。两个都不是好选择。

### 3.5 几个容易被忽略的细节

- **ERROR/FATAL 立刻 `fflush`。** 因为进程很可能紧接着就崩了，留在用户态缓冲区里的日志等于没写。
- **空闲 1 秒主动刷盘。** 后台线程用 `wait_for(1000ms)`，超时即视为空闲并 flush。这样 `tail -f` 能看到实时日志；否则 256KB 全缓冲可能让日志「延迟几分钟才出现」，排查时非常误导人。
- **单消费者让输出天然串行。** 只有一个线程写文件/stdout，所以不需要为输出加锁，也不会出现两条日志交错。
- **消息不静默截断。** `vsnprintf(nullptr, 0, ...)` 先问长度，再按需分配。用固定 1024 字节缓冲区「够用就行」，迟早会在打印 SQL 或长报文时把关键内容截掉，而现场恰恰是最需要完整信息的时候。
- **时间戳统一 UTC（呼应 ADR-14）。** 日志、数据库、接口全是 UTC，只在展示层本地化。否则跨时区/跨夏令时排查问题时会怀疑人生。
- **线程 id 用 `gettid()` 而不是 `std::thread::id`。** `std::thread::id` 只是个不透明的对象，而内核 tid 正是 `gdb`、`perf top`、`strace -f` 里显示的那个数字——排查多线程问题时要能对上号。用 `thread_local` 缓存，避免每条日志都做一次系统调用。
- **未初始化/已关闭时降级写 stderr。** 启动早期（还没 init）和关闭之后（已 shutdown）的日志不会丢，也不会去碰已经被关掉的文件句柄。
- **日志是唯一的全局单例。** 逐个把 `Logger&` 传进每个函数会污染所有签名却没有任何收益。单例在这里是「横切关注点」的合理用法，但换成别的场景（如连接池）就不合适了——那应该显式注入。

### 3.6 性能上还留着什么（P11 再动）

当前每条日志至少有一次 `std::string` 构造、一次 `deque` 节点分配、两次加锁（入队与出队各一次临界区）。真正压测时如果日志成为瓶颈，优化顺序是：① 前端缓冲 + 批量换缓冲（双缓冲）→ ② 定长环形缓冲 + 二进制定长记录，避免 `std::string` 分配。**先测量，再优化。**

## 4. 信号处理：为什么 handler 里只能写一个 `sig_atomic_t`

`onSignal()` 里只有一句 `g_stop = 1;`，这不是偷懒，而是硬约束：

- POSIX 只保证 **async-signal-safe** 的函数可以在信号处理器里调用。`printf`、`malloc`、`std::string`、日志（内部有锁和内存分配）都**不在**这个名单里。
- 危险场景：主线程正在 `malloc` 内部持有堆锁时被信号打断，处理器里再调 `malloc` → **死锁**。日志里的 `std::mutex` 同理：若信号打断了持有该锁的线程，处理器里再入队就自锁。
- 正确姿势：处理器只设置一个标志位（`volatile sig_atomic_t` 的读写是原子的），真正的清理与日志回到主循环执行。

另外两个刻意的决定：

- **不设 `SA_RESTART`。** 这样阻塞中的系统调用会返回 `EINTR`，主循环能立刻看到信号。P1 之后 `epoll_wait` 同样受益。
- **忽略 `SIGPIPE`。** 向已关闭的对端写数据时，默认动作是**直接杀死进程**。网络服务必须忽略它，改为检查 `write()` 返回的 `EPIPE` 来处理这一条连接。这是很多新手服务器「莫名其妙自己挂了」的元凶，P1 会正面用到。
- P1 起会换成 `signalfd`：把信号变成一个可读的 fd 交给 epoll，彻底避免「异步信号打断事件循环」这一类问题。

## 5. 配置系统

- **优先级**：环境变量 > `secrets.conf` > `server.conf` > 代码默认值。环境变量映射规则 `server.port → COFINANCE_SERVER_PORT`，这样容器/CI 里注入密钥不需要写文件。
- **只支持整行注释，不支持行内注释。** 取舍理由：`db.password=P@ss#1` 这种值会被「遇到 # 就截断」的解析器悄悄改成 `P@ss`，然后表现为「密码明明对却连不上」——排查成本极高。少一个便利特性，换掉一类玄学问题。这条已写成单元测试回归点。
- **`validate()` 里那份范围检查表同时充当必填项清单。** 少一个键就报一个错：配置文件不完整本来就是「不该启动」的状态。这是 fail fast 的具体落地——**宁可启动失败，也不要带着半套配置跑起来，然后在半夜以更难看的方式炸掉**。
- **密码脱敏。** 启动横幅会打印全部生效配置（排查配置问题的第一手资料），但键名含 `password/passwd/secret/key/token` 的值一律替换成 `***`。**日志泄漏密钥是真实事故**，所以脱敏逻辑写在 Logger 之上、Config 之内，并有单测保证明文不出现。
- **P0 阶段 db 凭据缺失只告警不报错**（还没接数据库）；P3 接线后会升级为错误。这是「按阶段收紧校验」的一个例子。

## 6. CMake 里踩到的坑（详见 BUGLOG B-002）

`sanitizer` 插桩必须**编译期 + 链接期成对出现**，而且要覆盖所有链接到插桩代码的 target。最初用 `foreach` 逐个 target 加编译/链接选项，漏掉了测试 target，于是测试链接失败并报出几十行 `undefined reference to __asan_report_load8`。

正确做法是目录级的 `add_compile_options` / `add_link_options`，且必须放在**所有 target 定义之前**（它只对之后创建的 target 生效）。教训：**别用枚举 target 的方式维护全局性的构建开关。**

## 7. 环境注意事项（会在整个项目里反复遇到）

- **LeakSanitizer 在受限沙箱（ptrace）下不可用**，会直接报 `LeakSanitizer has encountered a fatal error`。两种应对：① `ASAN_OPTIONS=detect_leaks=0` 只关泄漏检测，其余 ASan/UBSan 检查照常生效；② 用 valgrind 做泄漏检查。**ASan 与 valgrind 不能同时启用**，所以维护了两个构建目录：`build/`（ASan+UBSan）与 `build-nosan/`（给 valgrind 用）。
- 沙箱内无法创建 socket（连 `bind` 本地端口都会被拒），所以从 P1 开始，**运行服务与压测需要提权执行**。

## 9. 面试可能的追问

1. **异步日志怎么保证不丢？** 答：不保证「一条不丢」，而是**分级保证**。DEBUG/WARN 队列满时主动丢弃并计数（可观测）；ERROR/FATAL 最多等 100ms，仍满则同步兜底。同时 shutdown 会排空队列，所以正常退出不丢日志。
2. **队列为什么不做成无界的？** 答：无界队列把性能问题变成 OOM 问题，故障模式更糟；有界 + 丢弃计数让故障可控可观测。
3. **为什么不用 spdlog？** 答：这是学习项目，日志器本身是「锁、条件变量、RAII、缓冲策略」的综合练习；另外 spdlog 的功能集（格式化、sink）远超我们所需，自己实现能完全掌控背压策略。真实生产项目里我会直接用 spdlog。
4. **信号处理器里为什么不能 `printf`？** 答：async-signal-safe 约束；`printf` 内部有锁与缓冲状态，可能死锁或破坏状态。只能写 `sig_atomic_t` 标志位。
5. **`PUBLIC`/`PRIVATE`/`INTERFACE` 的区别？** 答：`PRIVATE` 只用于自身编译；`INTERFACE` 只传递给消费者、自己不用；`PUBLIC` 两者都要。头文件目录用 `PUBLIC`（消费者也要能找到头文件），内部依赖用 `PRIVATE`。
6. **为什么日志时间戳用 UTC？** 答：与存储、接口保持同一时间基准，避免时区/夏令时导致的错乱；本地化只放在展示层。

```bash
cmake --build build -j16            # 期望：零告警零错误

# ② 单元测试
ASAN_OPTIONS=detect_leaks=0 ./build/cofinance_tests
# 期望：=== 检查点 56 个, 失败 0 个 ===

# ③ 优雅退出（后台起，发 SIGINT，看退出码）
./build/cofinance & PID=$!; sleep 3; kill -INT $PID; wait $PID
# 期望：退出码 0；stdout 末尾出现「CoFinance 已优雅退出」

# ④ 泄漏检查（ASan 与 valgrind 不能同时用，故用独立构建目录）
cmake -S . -B build-nosan -DCOFINANCE_SANITIZE=OFF && cmake --build build-nosan -j16
timeout -s INT 9 valgrind --leak-check=full --error-exitcode=9 ./build-nosan/cofinance
# 期望：All heap blocks were freed -- no leaks are possible / ERROR SUMMARY: 0 errors
```
